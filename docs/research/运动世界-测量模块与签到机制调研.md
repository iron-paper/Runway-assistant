| 高德地图/导航 SDK | **使用，确认** | `libAMapSDK_NAVI_v10_0_700.so`（39 MB）、`assets/map_assets`、`assets/eyrie`、`assets/horusAssets`、`assets/navi` 离线地图资源 | 地图渲染、轨迹绘制、离线地图 |

## 三、测量模块拆解

### 3.1 定位链路（GNSS / AGPS / 网络定位）

**SDK 与进程**

- 高德定位/导航 SDK：`libAMapSDK_NAVI_v10_0_700.so`（arm64 单库约 39 MB），清单内注册 `com.amap.api.location.APSService`，`foregroundServiceType=0x00000008`（location）。
- 应用自有前台服务：
  - `service.RunLocationService`：`android:persistent="true"`、`priority=1000`、`foregroundServiceType=0x00000009`（dataSync|location）——跑步期间持续定位的核心载体。
  - `service.PluginRunService`：`foregroundServiceType=0x00000009`，插件化跑步服务。
  - `service.DaemonService` / `DaemonJobService`：保活。
- 高德 Key 硬编码于清单：`com.amap.api.v2.apikey = 696b79d71db0568d0607624d7c0d4f4a`（公开可读，属客户端常规配置）。

**权限面**

`ACCESS_FINE_LOCATION`、`ACCESS_COARSE_LOCATION`、`ACCESS_BACKGROUND_LOCATION`、`FOREGROUND_SERVICE_LOCATION`、`ACCESS_LOCATION_EXTRA_COMMANDS`、`ACCESS_GPS`、`ACCESS_ASSISTED_GPS`、`ACCESS_WIFI_STATE`/`CHANGE_WIFI_STATE`（辅助定位）。

**定位质量控制（资源字符串直接可见）**

| 资源名 | 文案 |
|---|---|
| `txt_gps_good` | GPS信号良好 |
| `txt_gps_normal` | GPS信号较为稳定 |
| `txt_gps_bad2` | 信号差 |
| `txt_gps_bad` | **无信号，正在用计步器估算** |
| `txt_gps_lose` | GPS信号丢失 |
| `txt_search_gps` | 正在努力定位中，跑步将在定位… |
| `msg_no_gps` / `no_gps` | 需要开启GPS定位功能 / 定位服务未开启 |

其中“无信号，正在用计步器估算”是判断其**融合策略**的关键证据：GNSS 质量下降时切换到计步推算，而非依赖陀螺仪惯导。

**轨迹与离线能力**

- 离线地图资源：`assets/map_assets`（101 个文件）、`assets/eyrie`、`assets/horusAssets`、`assets/navi`；资源串 `txt_offline`、`title_download_offline_map`、`no_offlinemap` 对应“离线地图下载/删除”。
- 断网跑步：`run_detail_saved_local_campus`、`run_detail_saved_local_outdoor` 表明轨迹可本地暂存，**3 天内**补传（“跑步数据已暂时保存至本地，请于三天内上传”）。
- 配速：`txt_speed_avg`（平均配速）、`txt_speed_operate`（瞬时配速）、`run_detail_unit_per_km`，由定位点距离/时间计算。

**判定**：定位是跑步成绩的第一数据源，采样与上传由前台服务维持；后台定位、悬浮窗、无障碍、电池优化白名单等一整套保活文案（`dialog_flow_message`、`four_pilcrow`、`location_background_content` 等）说明其对“持续定位不中断”的强依赖。

### 3.2 惯导与步态模块（重点回答“有没有惯导”）

**先给结论：没有实现严格意义上的惯性导航（INS/捷联惯导）。** 依据：

1. 清单未声明陀螺仪/磁力计硬件特性：`uses-feature` 仅 `stepcounter`、`stepdetector`、`bluetooth`、`camera`、`camera.autofocus`。
2. 无 `Sensor.TYPE_GYROSCOPE`/`TYPE_ROTATION_VECTOR` 相关字符串命中（业务代码加固，但硬件特性与权限层面已排除强依赖）。
3. 定位丢失时的兜底文案是“用计步器估算”，属于**步数×步长的航位推算（PDR-lite）**，不是对角速度积分。

**实际使用的传感器与指标**

| 能力 | 证据 | 说明 |
|---|---|---|
| 系统计步 | `stepcounter`/`stepdetector` 硬件特性；`BODY_SENSORS`/`BODY_SENSORS_BACKGROUND`；“正在用计步器估算” | 步数、步频的底稿数据 |
| 活动识别 | `ACTIVITY_RECOGNITION` 权限 | 判断步行/跑步/骑行等状态，服务端也会做行为特征复核 |
| 步频 | `run_detail_step_freq_format="%d 步/分钟"`、`txt_detailed_chart="步频/配速详细图表"`；Flutter 侧 `pages/charts/step_freq_chart.dart`、`StepFreqData`、`StepLimitLinePainter` | 展示与规则校验双用途 |
| 步幅 | `run_detail_stride_format="%d 厘米"` | 通常由 里程/步数 推算 |
| 爬升 | `run_detail_ascent_format="%d 米"` | 一般取 GPS 海拔序列累计 |
| 功率 | `run_detail_power_format="%d 瓦"` | 依据配速/体重等的估算值 |

**与高德 SDK 的关系**：`libAMapSDK_NAVI_v10_0_700.so` 内含 `VDR`/`DR`（卫星+陀螺航位推算）、`GyroBias`、`vdr_sensor_params` 等字符串，这是**导航 SDK 自身**在隧道/弱信号场景的能力；跑步模块是否启用其 DR 通道，静态层面没有直接证据，从其“计步器估算”文案看，跑步链路走的是自有计步兜底。

**规则侧（公开资料）**：有效步频区间常见为 **40–300 步/分钟**，配速区间常见 **2–10 分钟/公里**（各校略有差异），与 App 内“学校要求步频范围在…/学校要求配速范围在…”（Flutter 快照字符串）一致。

## 四、跑步过程中的签到

### 4.1 点位签到（跑步主签到）

这是“跑步签到”的本体：服务端按校区电子围栏随机下发点位，客户端用定位判断是否“经过”，经过后点位点亮并上报。

| 跑步模式 | 组件 | 点位规则（公开规则 + App 字符串） |
|---|---|---|
| 随机终点 | `RunRandomActivity` | 5 个点位中至少经过 **1 个必经点 + 2 个普通点**，普通点顺序不限；`txt_school_run="随机终点"` |
| 顺序跑 | `RunSequenceActivity` | 按 1→2→3… 顺序通过；`msg_finish_sequence_unfinished="本次跑步未按顺序通过点位…"`、`run_pass_sequence="按点位顺序跑"` |
| 自由跑 | `RunFreeActivity` | 无点位要求；`run_free_tip="自由跑模式无需经过任何点位"` |
| 一起跑（约跑） | `RunRandomActivity` + 房间 | 经过设定的 **2 个普通点**并回到终点；`msg_due_run_end_pass_uncomplete` |
| 学分跑/户外跑 | `CreditRunActivity` / `OutdoorRunActivity` | 同上体系，规则由学校配置 |
| 终点判定 | 全部模式 | 需进入终点范围；`msg_not_around_end="本次跑步未在终点范围结束…"`、`run_around_end_point="在终点结束"` |

**校验要素（资源字符串逐条对应）**

- 必经点：`txt_assess_point="路线必经点位"`、`run_pass_asses="经过必经点位"`、`msg_finish_uncomplete_assess_due="路线未经过必经点位，成绩无效"`。
- 普通点数量：`msg_finish_uncomplete_pass="本次跑步通过普通点位数小于2个…"`。
- 顺序：`msg_finish_sequence_unfinished`。
- 终点：`msg_not_around_end="本次跑步未在终点范围结束…"`、`run_around_end_point="在终点结束"`。
- 里程/时长：`msg_finish_uncomplete_dis`、`msg_finish_uncomplete_time`、`high_run_tip_desc`（跑步须知含目标公里数、单次最低里程、配速区间）。
- 点位获取失败：`msg_not_five_point="数据获取异常，点位获取失败，是否重新获取?"`（固定 5 点位的痕迹）。
- 点位奖励：`has_reward="您获得点位奖励…"`、`txt_get_random_gift="本次跑步经过的点位发现了一个随机奖品礼盒"`——经过点位即触发抽奖。

**技术实现**

- 点位集合由服务端按学校/校区下发（`msg_not_start_time`“地图信息获取失败”对应拉取阶段）。
- 客户端判定“到达”后调用原生校验：`libswsport.so` 导出 `Java_com_zjwh_sw_sport_SportJniUtils_isValidPoint`，同库还有 `getSecretKey`/`encodeByAES`/`md5`，即**点位合法性校验与上报签名在 native 层完成**，Java 层只做 UI 与流程。
- 通过记录、轨迹点、步频等一并上报，服务端二次复核（见第五节）。

### 4.2 跑中人脸抽检

- 触发：跑步过程中随机弹出（非固定点位触发），有语音与震动提示，需在限时内完成人脸采集。
- 证据：`FaceActivity`/`FaceContractActivity` + `CAMERA` 权限 + 高校通知明确“随机弹出人脸验证，未验证或验证错误本次跑步不达标”。
- 效果：未完成或比对失败，本次跑步不计成绩（高校通知口径）；抽检期间定位与轨迹仍在持续采集，轨迹连续性会影响判定。

### 4.3 课堂考勤签到（与跑步分离）

教师端发起考勤/点名，学生在有效区域与有效时段内完成签到、签退，按“停留时长”计有效出勤。

| 证据 | 内容 |
|---|---|
| 组件 | `AttendanceActivity`、`AttendanceListActivity`、`RollCallActivity`、`RollCallRecordActivity`、`CheckAttendanceActivity` |
| 文案 | “考勤期间请勿关闭程序，并保持蓝牙开启”“请在有效区域内进行考勤签到”“考勤有效时间至少达到 %d 分钟”“已进入签到范围/未进入签到范围”“签到时长: %d 分钟”“您的签到时长未到 %d 分钟，本次考勤将视为无效” |
| 判定要素 | 蓝牙（BLE 扫描）+ 地理围栏 + 最短停留时长 + 时段窗口（`attendance_not_over_time`/`attendance_time_out`） |
| 兼容提示 | 华为机型需打开“定位服务→提高精确度→蓝牙扫描开关” |

### 4.4 扫码签到

`utils.qrcode.ScanActivity`（扫码）、`mvi.me.QRCodeActivity`/`QRCode2Activity`（出示个人码）用于课堂点名、活动签到、体测检录等场景，属于“扫码即签到”的补充通道。

### 4.5 跑步签到链路（时序）

```
[开始跑步]
   │  拉取跑步配置/点位(服务端: 学校规则、5个点位、必经点、终点)
   ▼
RunLocationService(前台, location|dataSync) ── 高德定位回调 ──► 轨迹点/配速/里程
   │                                   │
   │                                   └─ GPS 质量差 ──► 计步器估算(步数×步长)
   ▼
每到一个点: 计算与点位距离 ──► isValidPoint(native) ──► 点亮/奖励 ──► 上报
   │
   ├─ 随机弹出人脸抽检(FaceActivity) ──► 通过则继续；失败/超时 → 本次成绩无效
   ▼
[结束] 校验: 必经点 + 普通点≥2(或顺序) + 终点范围 + 里程 + 时长 + 配速/步频区间
   │
   └─ 通过 → 服务端复核(环境/设备/行为特征) → 计入成绩；否则无效/待申诉
```

服务端并非只看客户端上报：公开公告明确“技术员按周复查数据源”，从配速、步频、路线、设备环境、账号登录行为多维度判作弊，异常则清除当周成绩。

## 八、给后续工作的建议

1. **要确认采样频率与传感器具体类型**：对 7.3.80 脱壳（爱加密 + 易盾），或真机 `dumpsys sensorservice` / `adb shell dumpsys location` 观察跑步时的传感器订阅与定位回调频率。
2. **要验证点位半径与顺序判定**：在测试校区用 mock 轨迹沿两点间插值，记录“点亮”阈值，可反推服务端半径配置。
3. **要验证人脸抽检触发策略**：多次跑步统计触发间隔与限时时长，判断是定时触发还是随机概率触发。
4. **要区分“跑步签到”与“考勤签到”**：前者是点位（GPS），后者是蓝牙+围栏+时长，二者数据链路与风控口径不同。
